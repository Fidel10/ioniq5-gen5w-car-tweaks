# Android Auto findings: the projection stack is missing

Status: **negative result / blocked** on the owner's EU `260128` firmware.
This is not a claim that AA is impossible on every Gen5W unit; it is what
this firmware and hardware expose.

## What is in the installed firmware

`/app/bin/AppProjection` (the projection host) loads:

- `libAirPlay`, `libAirPlaySupport`
- `libCarPlayAppFramework`, `libCarPlayMediaFramework`
- `libiAP2AppFramework-2.0`

There is **no Android Auto library, binary or string** in the installed
tree: no `CAndroidAuto*`, no `androidauto` file, no AA service. The vendor
projection path is AirPlay/CarPlay (iPhone) only.

The `CAndroidAutoInterface::setInstanceIWifiProjectionServiceCB` /
`CAndroidAutoMain+0x80835` gate that appears in AA research comes from a
**different firmware lineage**, not from this car's `260128` build. On this
unit it is not a flag to flip: the AA stack itself is absent. No DLT
`Fail to init Wifi Projection` messages exist because no AA projection
service runs.

## Hardware: AP+STA is available

The Wi-Fi chip is a **BCM4359 Rev 5** (driver 1.363.68, firmware
9.40.112.10). Relevant results:

```text
$ wl apsta
1

$ iw list | sed -n '/valid interface combinations/,/^$/p'
 * #{ AP } <= 2, #{ managed } <= 2, #{ P2P-client, P2P-GO } <= 2,
   #{ P2P-device } <= 1, #{ IBSS } <= 1,
   total <= 4, #channels <= 2
```

So the radio can run an AP for a phone **and** a managed connection at the
same time (two channels), which is what a wireless-AA design would need.
That hardware capability is not the blocker.

## Bluetooth / SPP

The Bluetooth stack is Broadcom BSA behind a BlueZ-like D-Bus facade
(`vbtd-51`). On the owner's car the session bus exposed A2DP, AVRCP, HFP,
MAP and PBAP service objects, but **no SPP/SerialPort object** and no
`InterfaceName` for an RFCOMM channel. `vbtd` did not expose
`SerialPort`/`rfcomm` strings. AA wireless needs an RFCOMM/SPP handshake;
without an SPP service or a bridge to the expected tty, the AA transport is
not reachable. A real Android phone test would be required to see whether
an SPP object appears on demand; it was not performed.

## What would be needed

1. **An AA-capable projection stack**: obtain the AA libraries/service from
   a newer/other Gen5W firmware or write/port a compatible stack. This is
   the hard blocker; a Wi-Fi flag alone does nothing.
2. **Wi-Fi AP + DHCP + radio ownership**: the CarPlay/Wifi1b AP+DHCP code
   and the single-owner radio design are reusable; the hardware supports
   AP+STA.
3. **Credentials and the projection gate**: the newer firmware expects
   `CarWifiCredentials` and the optional Wi-Fi projection service callback;
   fill/set them only after the AA stack exists.
4. **SPP/RFCOMM path**: validate with a phone; if no SPP service exists,
   implement the profile or a bridge to the tty the AA stack expects.
5. **AA handshake/protobuf/TCP/video/audio** then belongs to the AA library;
   validate with a real phone, parked.

## What was not done

- No AA library or firmware was installed on the car.
- No phone/AA handshake was attempted.
- No vendor Wi-Fi projection service was enabled.
- No claim is made that the `CAndroidAuto` gate from another firmware will
  work on this one.

## Prior art

The related public research
[NecktiedHummingbird/ioniq-5-Reverse-Engineering](https://github.com/NecktiedHummingbird/ioniq-5-Reverse-Engineering)
targets the same EU `260128` userspace in QEMU and reaches the authentic
Home screen. Its public notes also document that the AU manual lists
Android Auto/CarPlay as **USB-cable** functions and that wireless support
is undocumented. Its VM/security work was useful prior art; it does not
publish a working AA stack for this firmware either. See
`docs/08-prior-art.md`.

## Bottom line

For this car, AA wireless is **not a tweak**: the projection software is
missing. The practical paths are an official/newer firmware with AA, or a
separate AA-capable device. Do not spend time on the Wi-Fi gate before the
AA stack exists.
